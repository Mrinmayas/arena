Executive summary

Why this is an asset, not a concept

The AI-Ops Automation Harness is a single, self-contained boilerplate for operations and back-office automations that run on an operator's machine. The shipped tool is deterministic, with no LLM at runtime, so every run is reproducible and auditable. "Agentic" means it is built with Claude Code, guided by conventions captured from how the operators actually work.

Architecture — a layered baseline

One legible spine; heavier capabilities are opt-in, never forced

The reference automations span a wide complexity range — from a self-contained Excel compiler to a multi-step portal workflow with human-in-the-loop. A single rigid template can't serve both. The harness is therefore layered: a small always-present spine, plus capability layers a developer switches on only when the use case needs them.

Your automation
automation/ — the one entry point run(inputs, outputs) (via uv run automate), plus your _transform.py (read/classify inputs) and _report.py (render output). Explicitly wired — no auto-discovery "magic".
Opt-in capabilities
Browser + Recorder (portal automation), Excel framework, Engine (multi-step Stage/Step orchestration with resume & human-in-the-loop). Pulled in only when needed — a simple compiler ships none of them.
Vendored core
core/ — audit, excel, portals, secretstore, engine, docs — the reusable, generic, brand-free machinery distilled from the team's trusted production tools. Copied into each repo (kept pristine; updated centrally, not hand-edited).
Design principle — legible over clever. The harness deliberately drops the source monorepo's auto-discovery registry in favour of one explicit wiring call. A copy-me starter should be something the next developer can read top-to-bottom, not reverse-engineer.

Two shapes, one spine

ShapeWhenWhat it uses
Simple (default)Excel compilers, single-pass tools, portal download-and-process The run() spine + Excel and/or Browser capability. No engine.
Orchestrated (opt-in)Multi-step workflows needing resume & review gates The core.engine Stage/Step layer on the same spine, adding the structured run store.

Distribution & scale

Each automation is its own self-contained repo (or a small folder within one), copied from this baseline and shipped to operator machines via uv. This keeps client environments isolated and every deliverable independently runnable — matching how the team already works across ~7–10 developers and many client repos.

Observability — who did what

The compliance backbone, uniform across every automation

For controls-sensitive processes the human-vs-automation split is not just logging — it is the reviewer sign-off artefact (a four-eyes control). A reviewer approving a run must see exactly which outputs the tool produced and which a person entered or approved. Every run therefore writes:

ArtefactContents
audit_logs/<ts>/audit.logHuman-readable, one line per event.
…/events.jsonlStructured stream; every event stamped actor: automation | human.
…/run_summary.jsonThe sign-off split — automation actions vs. human actions/approvals, counts, and status.
Uniform by design. Whether an automation uses the engine or not, the same audit_logs/ trail is produced — the engine bridges its events into the same audit stream. Observability is mandatory and identical everywhere; there is no "un-audited" path.
# attribute every action
audit.automation("classified 1,204 invoice lines", count=1204)
audit.human("j.doe", "approved the tie-out variance", amount="12.50")

Excel policy — one safe lane, a narrow escape hatch

The rule that prevented a whole class of production bugs

core.excel.render() is mandatory for all workbook generation. It replaced hand-rolled openpyxl cell-poking, which repeatedly caused corrupt files, data loss, and stale-formula bugs in production. A pandas model renders once to an atomic write; money is carried as Decimal throughout via coerce.money, never float.

✓ The safe lane

Build a SheetModel, render with core.excel.render(). Formulas go through the formula seam; headers inside ERP exports are located with compat.find_header.

⚠ The escape hatch

Raw openpyxl / xlwings-COM is allowed only for cases render() structurally can't express — in-place edits, live recalculation, .xlsm macros, huge templates — and money is still Decimal. COM paths are flagged Windows-only.

Engine & orchestration

Opt-in — for multi-step workflows with resume & review gates

When an automation is multi-step and needs resume or human-in-the-loop, it is built as a core.engine Automation([Stage([Step(...)])]) and run via run_automation(...). You get a structured runs/<run_id>/ store plus the same audit_logs/ trail for free — the engine bridges its events into the audit stream, so observability stays uniform. OpenTelemetry is optional.

Commands

uv sync                          # install core; add extras: --extra browser --extra pdf ...
uv run automate --help           # run the automation (the one console script)
uv run pytest                    # tests
uv run python -m recorder <url>   # record a portal flow (needs: --extra browser)

Note: automate is the only console-script entry in pyproject.toml; the recorder is invoked as a module (python -m recorder). A uv run record alias is added at spin-up when copier templating lands.

Capability extras

Core installs pandas + openpyxl only. Everything else is opt-in via uv sync --extra <name> — a simple compiler ships none of them.

The engine is not a dependency extra — it is stdlib-only and switched on per project at spin-up (copier needs_engine).

Where your code goes

  • _transform.py — read & classify the input files into a pandas model (read_table, compat.find_header, coerce.money).
  • _report.py — build a SheetModel and render once with core.excel.render().
  • automation.py::run(...) — the spine that opens the audit run and wires transform → report. No auto-discovery.
Ship checklist. Tests green (smoke + a tie-out test) · README filled · no client data / secrets / SSO profiles committed (git-ignored — keep it that way) · runs clean on a fresh machine via uv sync && uv run automate · code on a branch / PR.

The full runbook lives in docs/AUTHORING.md; house rules for the AI assistant live in CLAUDE.md.

Testing

Mandatory — a cents-level drift must fail the build

Tests live in tests/ and are not optional. Every automation ships at least a smoke test and one golden-file tie-out test that fails on a single cent of drift (Decimal compare). The harness itself is green across its core suite.

Test shapeWhat it protects
Pure-functionTransform / classification logic in isolation.
Golden-file tie-outExact output — reconciliation figures correct to the cent.
Safety-propertyInvariants that must never break (e.g. totals reconcile, no negative balances).
Engine end-to-endA full Stage/Step run resumes and audits correctly.

Current core suite: audit · excel · engine · docs — 20 tests passing.

Key decisions & rationale

The choices that shaped the baseline
DecisionRationale
Per-repo template, vendored coreSelf-contained, client-isolated, laptop-runnable deliverables — matching how the team ships. Central updates handled later via a template-update tool.
No discovery / explicit wiringA copy-me starter must be legible; the harness begins where the project's discovery phase ends.
One spine, engine opt-inServes both a simple compiler and a complex multi-step workflow without two divergent frameworks to maintain.
Observability mandatory & uniformThe human-vs-automation trail is a compliance requirement, not a nice-to-have — so it is never optional.
Excel: render() default + narrow escape hatchHonours the hard-won "no hand-rolled openpyxl" rule while still supporting COM / macros / in-place edits where genuinely required.
Safe .gitignore as a controlConfidential client data (inputs, outputs, audit logs) is kept out of version control by default.

Roadmap & appendix

What's next, and how the repo is laid out

Roadmap

Next — Worked example planned

Replace the placeholder report step with a real core.excel.render() implementation and add a golden-file regression test, proving uv run automate end-to-end on a laptop and giving authors a concrete example to copy.

Later — Template tooling deferred

Adopt copier when several instances exist: its update can push a core or skill fix into already-created repos — the fix for the "drifting copies" problem, at the scale where it starts to pay off. Today, a plain copy is sufficient.
